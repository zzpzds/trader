设计第三节：服务架构与数据流

两个 Railway 服务，通过 PostgreSQL（pg-boss）协作，无需直接通信。

📦 next-app
用户交互层
前端页面
・ 策略工坊（AI 对话 + 策略预览）
・ 回测中心（进度 + 结果图表）
・ 参数探索（Phase 2）
・ 持仓管理（Phase 2）
API Routes
・ Claude API 对话代理
・ 策略 CRUD
・ 触发回测 → 入队 pg-boss
・ 轮询回测进度（SSE）
📦 worker
计算层（24/7 运行）
Phase 1 任务
・ 消费 run-backtest 任务
・ 抓取并缓存行情数据
・ 执行回测引擎，写回结果
Phase 2 任务
・ 消费 run-optimization 任务
・ 定时信号监控（每 15min）
・ 触发通知 / 模拟仓自动成交
🔵 Phase 1 核心数据流：回测
用户点击"运行回测"
→
Web API 入队
run-backtest
→
Worker 消费任务
拉取行情 / 执行引擎
→
结果写入
backtests 表
→
前端 SSE 收到
完成事件，渲染图表
Web 和 Worker 不直接通信 — Web 写任务到 pg-boss，Worker 轮询消费，结果写回 PostgreSQL，Web 通过 SSE 监听 DB 变化。
🟡 Phase 2 信号监控流：实仓通知 vs 模拟仓自动执行
模拟仓
Worker 每 15min 检查 →
信号触发 →
自动在 trades 表写入成交记录 →
position 自动更新 →
创建 notification（告知用户已自动成交）
实仓
Worker 每 15min 检查 →
信号触发 →
仅创建 notification（提醒用户操作）→
用户手动在券商执行 →
用户在 App 手动更新持仓
💬 AI 策略生成流
用户描述策略
"均线金叉 + RSI"
→
Claude API
多轮对话补全细节
→
输出 Strategy JSON
前端实时预览
→
用户确认保存
→ strategies 表
Claude 收到的系统提示包含完整的 DSL Schema 定义，输出严格遵循该格式。修改已有策略时，将现有 JSON 连同对话发给 Claude，它直接返回更新后的 JSON。

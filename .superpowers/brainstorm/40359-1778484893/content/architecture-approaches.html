整体架构方案

云部署 + 长时任务（优化器）→ 需要后台任务队列。三种方案的核心差别在于如何处理这个问题。

A

单 Next.js 服务 + pg-boss 任务队列

一个 Railway 服务跑所有东西，用 PostgreSQL 自带做任务队列

Railway
📦 next-app（Web + API + Worker 线程）
🗄️ PostgreSQL（数据 + 任务队列）

用户触发优化 → pg-boss 入队 → Next.js 内 Worker Thread 消费

优点

  • 最简单，一个服务搞定
  • 无需 Redis，成本低
  • 部署维护最省心

风险

  • Worker Thread 与 Web 共享内存，优化器跑满 CPU 时影响响应速度
  • 单进程崩溃会中断进行中的优化任务
B

Next.js Web + 独立 Worker 服务 ★ 推荐

两个 Railway 服务，共享同一个 PostgreSQL，pg-boss 做协调

Railway
📦 next-app（Web + API）← 用户交互
📦 worker（Node.js）← 优化器 + 信号监控
🗄️ PostgreSQL（共享数据 + pg-boss 队列）

Web → pg-boss 入队 → Worker 独立消费 → 结果写 DB → Web 轮询进度

优点

  • Web 与计算完全隔离，互不影响
  • Worker 崩溃不影响用户界面
  • 信号监控 24/7 独立运行
  • 无需 Redis（pg-boss 用 PostgreSQL）

代价

  • 两个服务，Railway 费用稍高约 $10/月
  • 部署配置略复杂
C

Next.js + Python 优化器微服务

Worker 改用 Python + optuna，获得最佳贝叶斯优化质量

Railway
📦 next-app（Web + API）
📦 py-optimizer（Python FastAPI + optuna）
📦 ts-worker（Node.js，信号监控）
🗄️ PostgreSQL

优点

  • optuna 是工业级贝叶斯优化，质量最高
  • Python ML 生态随时可扩展

风险

  • 三个服务，复杂度跳升
  • 需维护两套依赖（TS + Python）
  • 回测逻辑可能需要在两端重复实现
⚠️ 关键可行性说明
方案 B 中的贝叶斯优化需在 TS 中自实现（约 300-400 行），TS 无现成的 Gaussian Process 库。这是整个项目技术风险最高的部分，但对于交易策略参数搜索（5-10 个参数，每次评估 <500ms）是完全可行的。

## Context

当前通知模块以侧边栏铃铛下拉面板形式存在（`NotificationPanel` 组件），功能有限：
- 点击通知仅跳转到 `/monitoring`，无法定位具体监控运行
- 无筛选、无删除、无批量操作
- 数据仅在页面加载时获取一次，无更新机制
- 下拉面板信息密度低，无法有效管理通知

现有数据库 schema 满足需求，无需变更。API 层需要增强筛选和关联查询能力，前端需要从下拉面板迁移为独立页面。

## Goals / Non-Goals

**Goals:**
- 将通知升级为独立菜单页面，与监控中心风格统一
- 提供完整的筛选（状态 + 策略）、批量操作（标记已读 / 删除已读）、单条删除能力
- 点击通知精确跳转到对应监控运行详情
- 侧边栏菜单项显示未读角标，实时反映通知状态

**Non-Goals:**
- 浏览器推送通知 / 邮件 / 外部消息渠道
- 通知偏好规则配置（只通知特定策略、只通知特定操作类型）
- 实时通知推送（WebSocket / SSE / 轮询）
- 通知分页加载（当前通知量不大，50 条限制足够）

## Decisions

### 1. 页面布局：列表页而非卡片流

**选择**：与监控中心一致的列表布局
**备选**：卡片流布局（每条通知为独立卡片）
**理由**：列表布局信息密度高、批量操作方便、与现有页面风格统一。通知量预计不大，卡片流的视觉优势不明显。

### 2. 筛选方式：服务端筛选

**选择**：通过 query 参数传给 API 做服务端筛选
**备选**：客户端筛选（一次加载全部通知，前端过滤）
**理由**：通知量当前较小（<50 条），客户端筛选也可行，但服务端筛选为未来扩展留有余地，且与监控中心的筛选模式一致。策略筛选需要 join monitoringRuns → strategies，客户端无法独立完成。

### 3. 点击跳转：跳转到 /monitoring 页面并高亮对应 run

**选择**：点击通知跳转 `/monitoring?runId=<id>`，监控中心页面接收参数后自动展开对应 run
**备选**：跳转到独立的 `/monitoring/runs/[id]` 详情页
**理由**：监控中心已有 run 列表和展开逻辑，复用现有页面更简单。通过 URL 参数传递 runId，页面加载后自动定位展开，无需新建页面。未来如有需要再拆分为独立详情页。

### 4. 未读角标更新：导航时刷新

**选择**：在侧边栏组件中，监听路由变化时重新获取未读数
**备选**：定时轮询 / 全局状态管理
**理由**：通知量不大，用户导航时刷新即可满足需求。定时轮询和全局状态增加了复杂度，当前阶段不需要。

### 5. 统计卡片数据：API 一次性返回

**选择**：GET `/api/notifications` 在返回通知列表的同时返回统计数字（unreadCount、todayCount、weekActionCount）
**备选**：独立统计 API
**理由**：统计数据来源相同、查询简单，一次请求减少网络开销。

## Risks / Trade-offs

- **[通知量增长]** → 当前 50 条限制和全量返回模式在通知量大时可能不够。缓解：短期内通知量不会激增（每日最多每个策略一条），需要时再加翻页。
- **[删除已读无确认]** → 用户误操作可能丢失通知。缓解：通知来源于监控运行，原始数据（monitoring_runs）不受影响，通知可由监控重新生成。
- **[角标延迟]** → 导航时才更新角标，用户可能在通知页操作后角标不同步。缓解：通知页操作后通过 Next.js router 事件触发侧边栏重新获取。
